# Project conventions

Решения о структуре проектов, которые пользователь принял один раз для всех проектов. Правила меняются со временем —
поэтому они лежат в одном файле, а не в памяти агента.

| Путь | Что |
|---|---|
| [rules.toml](rules.toml) | **единственный источник правды**: правила, зачем, как проверить, как исправить |
| [scripts/check.py](scripts/check.py) | детерминированная проверка по rules.toml, только stdlib |

## Перед работой — свежие правила

Скилл лежит в общем репозитории и синхронизируется между рабочими станциями. Если папка скилла — рабочая копия SVN
или git, сначала обнови её (`svn update` / `git pull` в корне репозитория скиллов), чтобы проверять по актуальным
правилам. Если обновить не удалось — скажи об этом и продолжай с локальной версией.

## Проверить проект

```bash
python <skill>/scripts/check.py <project>            # один проект
python <skill>/scripts/check.py --all <папка>        # все подпапки, сводка
python <skill>/scripts/check.py --json <project>     # для разбора
```

`ERR` — нарушение стандарта, `WRN` — стоит посмотреть, `--` — правило к проекту не относится.
Покажи пользователю отчёт коротко: какие правила нарушены и что конкретно не так.

## Привести к стандарту

Только по явному согласию пользователя, по одному правилу за раз:

1. Возьми `fix` нарушенного правила из rules.toml — это план. Посмотри реальные файлы проекта: план общий,
   проект конкретный (зависимости, ссылки, скрипты сборки, CI).
2. Скажи, что будет сделано, и дождись «да» — миграция меняет много файлов.
3. В SVN-проектах переименования и переносы — через `svn move` / `svn delete`, чтобы сохранить историю.
   Ничего не коммить.
4. После правок снова запусти `check.py` и убедись, что правило зелёное; для uv — что проект запускается.

Не начинай миграцию сам посреди другой задачи: если заметил нарушение, упомяни его одной строкой.

## Новый проект

Создавай его сразу по правилам: пройди по rules.toml и заложи всё, что `require`.

## Изменить правила

Когда пользователь принимает новое решение («теперь все проекты…»):

1. Добавь или поправь `[[rule]]` в rules.toml: `id`, `since` (сегодняшняя дата), `severity`, `title`, `why`,
   проверка (`applies_if_any` / `require` / `forbid` / `allow` / `forbid_text`) и `fix`.
2. Если проверку нельзя выразить этими полями — опиши её в `why`/`fix` словами и предложи расширить check.py.
3. Прогони `check.py` на паре проектов — правило должно ловить то, что задумано, и не ловить лишнее.
4. Напомни пользователю закоммитить репозиторий скиллов, иначе другие станции правило не увидят.
